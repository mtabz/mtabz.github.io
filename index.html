Featured build

MCPFence

Deterministic namespace defence for MCP vendors.

Closed · no-go decision

MCP software is discovered through package registries, server directories and remote endpoints. A vendor may publish its official server as @vendor/mcp or vendor-api-mcp, while an unrelated publisher controls vendor-mcp — the name a developer or agent is most likely to assume is official.

Outcome

The detection held up. Nobody needed to buy it.

In the final validation round I picked six vendors by hand. Every one had at least one confusable or uncontrolled name across npm, PyPI and the MCP Registry. AI agents produced those findings by applying a fixed custody rule; a separate agent re-graded each one blind, and a blind hunt for public evidence that would overturn them reversed none of the six.

Then I tested demand. I disclosed three findings to the vendors concerned: one closed it as a hardening suggestion rather than a vulnerability, one never replied, and none had fixed the gap when I made the call. I pressure-tested four buyer paths and none held. Vendor security teams treat a namespace gap as a suggestion. Developers who copy the install command from official docs never hit it. Agents resolved to the official server nearly every time. And the official MCP Registry already verifies namespaces at publish time, so the platform buyer was building the feature itself.

The roadmap had a gate: monitoring would only be built if paid audits showed recurring demand. The demand test failed before I reached a paid audit, so I wrote the no-go on 27 August 2026 and stopped building. One gap survived, watching for custody changes after publish, but it is only worth money with behavioural detection, which is a different product against funded incumbents. I recorded it and did not pivot into it.

The scanner keeps models out: registry facts plus a rule that only counts evidence that the vendor controls an asset, never evidence that the asset claims the vendor.

The risk it targeted

A malicious package can receive credentials and act under your brand.

A namespace gap gives a malicious publisher a credible way to masquerade as the vendor. In one real scan, the obvious package name was held by a third party that requested the vendor's API token and exposed tools capable of creating, deleting and reconfiguring infrastructure. A user or agent can select the wrong package, hand it privileged credentials and attribute the resulting incident to the vendor whose name it appears to carry.

MCPFence was built to give the vendor a deterministic, evidence-backed map of which identity surfaces it owns, which remain exposed, and which are already occupied, before a customer or agent discovers the wrong one.

How the evidence changed the product

I started with an AI warning tool. Testing pointed to a different customer and a simpler product.

The first concept was for developers and agents: an AI probe would search for an MCP server and warn when it appeared to have found an impostor. In 30 Sonnet trials, however, the probe reached the official server 29 times. That made user-side discovery mistakes a weak foundation for a product.

At the same time, deterministic scans found that three of seven vendors had an obvious package name already occupied by a third party. I followed the stronger signal: the vendor became the customer, and MCPFence became a reproducible audit of namespace ownership and provenance rather than an AI warning system.

The search probe still had a useful secondary role: testing how real agents behave when choosing between competing MCP identities. But Sonnet runs were expensive because web searches injected large amounts of content into the model context. A matched five-vendor Haiku test reduced measured cost to $0.063 per scan, but missed one official server that Sonnet found. I therefore kept models out of the customer-facing scan and kept the probe only as an evaluation tool. I never ran enough trials to set an accuracy threshold for it.

How I built it. A solo, agent-first build.

I owned the strategy, buyer and threat model, specified the resolution rules, safety boundaries and test corpus, and set the architecture. I then used AI as the execution layer to implement against that specification and hardened the product against adversarial fixtures.
